   PROBLEM STATEMENT
   =================
   The quicknxs application is being killed by the OOM (Out of Memory) killer with
   exit code 137 when performing "Smooth Off-Specular Data" operations on GUI.

   ROOT CAUSE: INADEQUATE MEMORY SCALING IN smooth_data() FUNCTION
   ================================================================

   The smooth_data() function in /home/bvacaliuc/Projects/Claude/quicknxsv1/quicknxs/qcalc.py
   was designed for small datasets (test case: 10,000 points) but is being called with
   extremely large datasets (35,000,000+ points), causing catastrophic memory bloat.

   CRITICAL FINDING #1: THE HOTSPOT (qcalc.py lines 285 & 287)
   =============================================================

       rij = (x-xij)**2/ssigmax + (y-yij)**2/ssigmay

   This single line creates 6-7 temporary arrays for EVERY grid point iteration.

   Scenario:
   - Input data: 35 million data points (not uncommon for combined off-spec datasets)
   - Each array: 35M × 8 bytes (float64) = 280 MB
   - Temporary arrays per line: 6-7 arrays = 1.6-2 GB per iteration
   - Grid points: 100 × 100 = 10,000 total
   - Memory required for complete execution: IMPOSSIBLE (would need 16-20 GB)

   Timeline to OOM:
     Iteration 0-500:   Garbage collection manages memory, but fragmentation begins
     Iteration 500-1000: Memory fragmentation severe, malloc fails on heap
     Iteration ~1000:   OOM killer triggered (process exits 137)
     Progress completed: ~10% of smoothing grid
     Symptom: Process hangs/freezes then dies abruptly

   CRITICAL FINDING #2: DATA PREPARATION INFLATES ARRAY SIZE (qio.py line 737)
   =============================================================================

       data = np.hstack(odata[channel])

   The odata[channel] contains a LIST of off-specular datasets from multiple runs.
   hstack() creates one MASSIVE temporary array containing all data concatenated.

   Data composition:
     - detector x-pixels: 304 pixels
     - detector y-pixels: 256 pixels
     - Time-of-flight bins: 100-200 bins
     - Per detector scan: 304 × 256 × 150 = 12.3 million data points
     - Multiple datasets combined: 2-4 datasets × 12.3M = 24-50 million points
     - Channels: potentially 4 channels (++, --, +-, -+)

   Then flattened:
     - x = data[:, :, 4].flatten()  → 35M elements
     - y = data[:, :, 1].flatten()  → 35M elements
     - I = data[:, :, 5].flatten()  → 35M elements

   Total: 105M float64 values = 840 MB just for input, before any processing.

   CRITICAL FINDING #3: INNER LOOP DOES NOT SCALE (qcalc.py lines 270-293)
   ==========================================================================

   The nested loop has O(N×M) complexity where:
     - N = number of input data points (35 million)
     - M = number of grid output points (10,000)

   For each grid point, a FULL-SIZED rij array is allocated and computed.
   This is fundamentally unscalable for large datasets.

   Pseudocode issue:
       for each grid_point (10,000 iterations):
           rij = full_sized_array_operation(N)  # N = 35 million
           memory_peak = baseline(840MB) + rij(280MB) + temps(1.5GB) = 2.6 GB

   After 500 iterations of this cycle with garbage collection and heap fragmentation,
   malloc starts failing on requests for 280MB contiguous blocks.
